### 根因 1（硬 bug）：`BaseEdge` 的 `markerEnd` 传了对象

React Flow 12.12 的 `EdgeWrapper` 会把 **edge 对象**上的 `markerEnd` 预先转成字符串再交给自定义边：

```js
// @xyflow/react/dist/esm/index.js, EdgeWrapper
const markerEndUrl = edge.markerEnd ? `url('#${getMarkerId(edge.markerEnd, rfId)}')` : undefined;
<EdgeComponent ... markerEnd={markerEndUrl} ... />
```

`getMarkerId({type:'arrowclosed'}, '1')` → `1__type=arrowclosed`（`@xyflow/system` `getMarkerId`：`${id}__${Object.keys(marker).sort().map(k=>k+'='+marker[k]).join('&')}`）。
`MarkerDefinitions` 据此渲染 `<defs><marker>`；项目在 edge 对象上确实设了 `markerEnd: { type: MarkerType.ArrowClosed }`
（`journey-map-graph.ts:518,586`；`useJourneyWorkflowEditor.ts:345,368,390,403,742`），所以 def 是有的。

但 `JourneyFlowEdge.tsx:49` **丢掉了传进来的 `markerEnd` 字符串**，自己新造对象：

```tsx
<BaseEdge markerEnd={{ type: MarkerType.ArrowClosed, width: ..., height: ..., color: ... }} />
```

`BaseEdge` 内部 `{...props}` 直接 spread 到 `<path>` → React 序列化成 `marker-end="[object Object]"` → 无效 URL → 丢弃。

附带结论：
- `color/width/height` 写在 `BaseEdge` 的 prop 上**完全无效**。只有写在 edge 对象的 `markerEnd` 里才会进 `createMarkerIds`。
  所以那个 marker 的色是 `defaultMarkerColor` = `rgb(177,177,183)`，跟组件想设的 `#94a3b8 / #1677ff` 无关。
- `<Marker>` 默认 `markerUnits="strokeWidth"`（`markerWidth/Height = 12.5`，`viewBox="-10 -10 20 20"`，`orient="auto-start-reverse"`），
  箭头大小跟 `stroke-width` 绑定，改 `width/height` 也不是直观的像素。
- 正确写法就是把传进来的 `markerEnd` 透传：`<BaseEdge markerEnd={markerEnd} />`。

### 根因 2：label 不是 edge label，是 node 里的 HTML span

`JourneyFlowEdge` 现在只画 `BaseEdge`（`1ff76fb` 起 outcome 文本被删）。分支名改挂在
`JourneyFlowNode.tsx:199-217` 的 `.journey-flow-source-label`，位置由 `handleStyle(index,total)`
（`top = (index+1)/(total+1)*100%`）决定，CSS 是 `right:-8px; transform: translate(100%,-50%)`。

它在 `.react-flow__viewport` **内部**，跟着画布一起缩放 → zoom 0.263 下 10px 字变 2.63px、
`max-width:72px` 变 19px。位置是对的（实测没被遮、没重叠、没截断），但**不可读**。
这就是「edge label 显示总有问题」的直接原因。

标准解法是 `EdgeLabelRenderer`（渲染到画布变换之外的 portal，字号不缩放）。项目文档里写过它
（`docs/journey-workflow-editor.md:190,200,699`），组件里没用。

## 排查「Timeout after 300000ms waiting for session.idle」

结论：这不是本项目的错误文案，是 `@github/copilot-sdk` 1.0.16（CLI 1.0.90）在
`CopilotSession.sendAndWait()` 里抛的。300000 是**本项目的默认值**（`TURN_TIMEOUT_MS`，
`src/config.ts` 默认 300_000），SDK 自己的默认是 60000。

调用点：`src/agent/copilot.ts:399` `session.sendAndWait({ prompt }, config.turnTimeoutMs)`。

SDK 实现（`node_modules/@github/copilot-sdk/dist/session.js`，逐字）：

```js
const effectiveTimeout = (typeof schemaOrTimeout === "number" ? schemaOrTimeout : timeout) ?? 6e4;
...
const unsubscribe = this.on((event) => {
  if (event.agentId) return;                                    // 子 agent 事件被丢
  if (event.type === "assistant.message") lastAssistantMessage = event;
  else if (event.type === "session.idle" && event.data.mode !== "autopilot")
    resolveOutcome({ kind: "idle" });                            // autopilot idle 不算完成
  else if (event.type === "session.error") resolveOutcome({ kind: "error", error });
});
await this.send(options);
const outcome = await Promise.race([outcomePromise, timeoutPromise]);
```

要点：
- 这是**整轮墙钟**计时器，不是「空闲 5 分钟」。send 之后开表，`finally` 里清。
- `session.idle` 的语义（`IdleData` 注释）= 「没有后台 agent、没有挂着的 shell 命令在跑」。
- `SessionMode = "interactive" | "plan" | "autopilot"`；autopilot 的 idle 被跳过 → 必然跑满超时。
- `event.agentId` 非空的事件全部忽略 → 若本轮由 `task` / `read_agent` 子 agent 驱动，root 长期不 idle。

本项目侧的可疑点（未改）：
- `src/agent/copilot.ts:27` 的 `WORKBENCH_TOOLS` 白名单**包含 `ask_user`**，但 `sessionConfig`
  没有 `onUserInputRequest`。SDK `_handleUserInputRequest` 无 handler 时直接
  `throw new Error("User input requested but no handler registered")`，错误经 JSON-RPC 回给 CLI，
  是变成工具失败还是挂住取决于 CLI —— 是条需要单独验证的路径。
- 也没有 `onPermissionRequest`（SDK 会把 `undefined` 注册进去），权限提示是另一条静默挂起路径。
- `graphify` MCP 若卡住不返回，`session.idle` 永远不来 → 同样表现为超时。

现有处理是对的：`src/agent/copilot.ts:432` 用精确正则
`/^Timeout after \d+ms waiting for session\.idle$/` 匹配后 `session.abort()`。SDK 的 typings
明确写了超时「不会中止已在跑的 agent 工作」，不 abort 就会出现「DB 记 failed、agent 还在写文件」。

排查顺序：`TURN_TIMEOUT_MS=600000` 排除「真的只是慢」→ 看 trajectory 最后一条 tool_call 停在哪
（停在 `ask_user` / `task` / MCP 就是对应原因）→ 打 `session.idle` 的 `{aborted, mode}` 日志。
