# LLM 执行分析报告：CodeBuddy、jevSmartFunc 与其它模型调用

审查日期：2026-10-07
审查范围：`src/agent/`（runtime、codebuddy、copilot、opencode、jev-smart-func）、`src/workflow/`（ask、mission-*、journey-ai）、`src/analysis/reviewer.ts`
对照基线：ADR-028（Runtime 选择与 fallback）、ADR-029（失败语义跨 Runtime 一致）、ADR-014（概率 Agent 与确定性 Gate）
方式：只读分析，未修改任何仓库文件。最近提交 `2199d82` / `2ace09e` 刚为 CodeBuddy 和 Smart Function 做了结构化输出适配，本报告基于该状态。

---

## 摘要

三条运行时的"主 Agent 执行"骨架是清楚的：`runtime.ts` 统一了模型解析和 quota fallback，业务状态由 workflow 层持有。真正的问题集中在 **主 Agent 之外的模型调用**——也就是 `jevSmartFunc`、Reviewer、人格渲染、陪伴提示这些"辅助判断/表达"调用。

一句话结论：**这些辅助调用沿用了"完整 Agent"的执行方式，却没有沿用"完整 Agent"的边界。** 在 Copilot 上它们被收紧了工具面；在 CodeBuddy 和 OpenCode 上，它们拿到的是自动放行、带全部内置工具的完整 Agent。同时，这些辅助判断的失败方式被硬耦合进主流程——一次 JSON 格式偏差就能把整轮调查卡死。

共 3 条严重、6 条中等、3 条轻微。三条严重都只影响 CodeBuddy / OpenCode，不影响 Copilot 默认路径，因此日常在 Copilot 上跑不容易发现。

---

## 严重

### S1. 辅助判断调用在 CodeBuddy / OpenCode 上能执行任意工具，且自动放行

`jevSmartFunc` 的设计边界写得很明确（`src/agent/jev-smart-func.ts:767-776`）：

```ts
'你是一个 Decision Function，不是聊天助手。',
'不要调用工具，不要继续调查，不要输出解释性文章。',
```

但这只是 prompt。实际执行走 `askAgentWithFallback`（`src/agent/jev-smart-func.ts:791-799`），runtime 由模型决定。当 Investigation 选的是 CodeBuddy 时，它落到 `askCodeBuddy` → `runCodeBuddyQuery`，而 `queryOptions`（`src/agent/codebuddy.ts:197-298`）**没有设置 `tools` 或 `disallowedTools`**：

```ts
permissionMode: (input.permissionMode ?? 'allow_all') === 'allow_all'
  ? 'bypassPermissions' as const
  : 'default' as const,
// ...没有 tools / disallowedTools
maxTurns: config.codeBuddyMaxTurns,   // 默认 200
```

CodeBuddy SDK 自己的类型注释（`node_modules/@tencent-ai/agent-sdk/lib/types.d.ts:1004-1010`）说得很清楚：

```
- undefined (default): Use all available built-in tools
- []: Disable all built-in tools
```

所以一个"Decision Function"在 CodeBuddy 上实际拥有 Bash / Read / Write / Edit 等全部内置工具，权限是 `bypassPermissions`，工作目录是 Investigation workspace，而且 `canUseTool` 对一切返回 `allow`（`src/agent/codebuddy.ts:293-296`）。`jevSmartFunc` 又不传 `missionActionGate`，所以连那唯一的兜底 Gate 也没有。

OpenCode 同样：`askOpenCode` 对 `purpose: 'review'` 只关掉 Graphify（`src/agent/opencode.ts:890-892`），CLI 仍以 `--auto` 启动（`src/agent/opencode.ts:963`）。`opencode run --help` 对该参数的原文是：

```
--auto  auto-approve permissions that are not explicitly denied (dangerous!)
```

对比 Copilot 路径：`purpose: 'review'` 会让 `isolatedPurpose` 为真，`availableTools` 被换成空的 `new ToolSet()`，且不注入本地数据工具（`src/agent/copilot.ts:769-770`）。三套运行时对同一个"决策调用"给出了三种不同的工具边界。

**影响**：`jevSmartFunc`、`reviewArtifact`（`src/analysis/reviewer.ts:147-156`）、人格渲染（`src/workflow/ask.ts:880-892`）、陪伴提示（`src/workflow/ask.ts:281-287`）在 CodeBuddy / OpenCode 上都有能力读写工作区、执行命令，且无需用户确认。这与 ADR-028 §3 用 `bypassPermissions` 时"以宿主 Mission Action Gate 为对价"的前提不符——恰恰是这些调用没有那个 Gate。

**方向**：给 review / journey-map 这类 `purpose` 在 CodeBuddy 上显式设置 `tools: []`（或在 `askCodeBuddy` 里按 `purpose` 统一收敛），OpenCode 侧对应地不启用 `--auto` 或把 agent 的工具面收窄。把"结构化判断调用"和"调查调用"的工具策略分开，而不是靠 prompt 约束。

### S2. Smart Function 一次失败会拒绝所有工具，把格式问题升级为整轮失败

`ask.ts` 的 Mission 行动闸门在拿不到判断结果时选择"停"（`src/workflow/ask.ts:550-561`）：

```ts
if (!review) {
  recordTrajectory({ ... name: '这一步暂时无法执行，已经暂停' ... });
  return { allowed: false, reason: '助手暂时无法确认这一步是否有助于完成当前任务，因此先停在这里。' };
}
```

而 `reviewMissionAction` 的 `null` 覆盖了**所有**异常，不只是服务不可用（`src/agent/jev-smart-func.ts:576-579`）：

```ts
} catch {
  // Smart Function 不是权限边界；不可用时不伪装成"业务判断通过"，交给 Stage Gate 做最终兜底。
  return null;
}
```

抛出的异常包括结构化校验失败：`choice 超出候选项`、`概率和必须约等于 1`（`src/agent/jev-smart-func.ts:355,375`）。在 CodeBuddy / OpenCode 上，`responseSchema` 只是被拼进 prompt 文本（`src/agent/codebuddy.ts:211-216`、`src/agent/opencode.ts:555-559`），没有原生结构化输出约束，模型返回的概率不严格归一或选错候选的概率明显高于 Copilot。而概率和容差只有 0.03。

结果是：模型只要在这一次判断上格式偏了一点，行动闸门就 deny 第一个工具；`missionActionReviewed` 只在允许时置位（`src/agent/codebuddy.ts:290`、`src/agent/copilot.ts:658-660`），所以模型换一个工具重试时会**再触发一次判断、再 deny 一次**。最终这一轮要么耗尽 6 分钟超时（Copilot），要么在没有可用回答的情况下结束。

**同一套 Smart Function，三种失败策略**：

| 调用 | 失败时 | 位置 |
|---|---|---|
| Mission Clarity | 放行（null → 接受 Mission） | `src/workflow/mission-evaluation.ts:99-101`、`src/server.ts:508` |
| Mission Completion | 拒绝完成（安全） | `src/workflow/mission-completion.ts:163-173` |
| Mission Action Gate | 拒绝全部工具（最硬） | `src/workflow/ask.ts:550-561` |
| Unknown Impact | 保留原状（中性） | `src/agent/jev-smart-func.ts:691-694` |

ADR-028 §2 明确要求"业务逻辑错误不能被静默覆盖"。这里反过来：辅助判断的**格式错误**被当成"任务无法继续"，覆盖了整个调查。至少要区分"服务不可用"和"结果不合规"——后者应该重试一次或降级，而不是直接卡死主流程。

### S3. CodeBuddy / OpenCode 没有执行超时，只有 Copilot 有

`config.turnTimeoutMs`（默认 360s）只在 Copilot 里使用：

```
grep 结果：turnTimeoutMs 仅出现在 src/agent/copilot.ts:813,817,1670,1672
```

Copilot 有一套独立 watchdog（`src/agent/copilot.ts:806-819`，`setInterval(executionWatchdog, 250)` 于 `:1393`），并且区分执行超时、权限等待、用户输入等待三种预算。`askCodeBuddy`（`src/agent/codebuddy.ts:183-468`）和 `askOpenCode`（`src/agent/opencode.ts:657-872`）**都没有任何墙钟超时**：只有 `shouldAbort` 协作式取消、`maxTurns`（CodeBuddy）和 `--auto`。

**影响**：CodeBuddy SDK 或 `opencode run` 子进程一旦卡住（网络挂起、CLI 死锁、模型无响应），这一轮 Investigation 会无限等待。用户只能手动 Stop，而且没有"卡了多久、卡在哪一步"的超时语义。这与 ADR-029 §7"三种 Runtime 使用相同的失败语义"不一致——目前只有 Copilot 有执行超时这一层语义。

**方向**：把执行 watchdog 提到 runtime 层（`runtime.ts`），三套 adapter 共享同一个 `turnTimeoutMs` 预算，CodeBuddy/OpenCode 在超时时 abort 并抛出与 Copilot 一致的超时错误。

## 中等

### M1. 辅助判断调用不传 runtime，可能与 Investigation 选择的 runtime 不一致

主 Agent 调用显式传了 runtime（`src/workflow/ask.ts:500`）：

```ts
runtime: control.agent.runtime,
```

但所有辅助调用只传 `model`，不传 runtime：行动闸门（`ask.ts:544`）、Unknown（`:597`）、Alignment（`:629`）、Completion（`:669`、`:802`、`:935`）、人格渲染（`:889`）、`jevSmartFunc` 内部（`jev-smart-func.ts:791-799`）。

`askAgentWithFallback` 的选取规则是（`src/agent/runtime.ts:169-171`）：

```ts
const selectedRuntime = input.runtime ?? runtimeFromModel(input.model) ?? config.agentRuntimeDefault;
```

当 `control.agent.model === 'auto'` 且 `control.agent.runtime === 'codebuddy-sdk'` 时，`runtimeFromModel('auto')` 返回 `undefined`，于是辅助调用落到 `config.agentRuntimeDefault`（默认 `copilot-sdk`）——**用户明确选了 CodeBuddy，内部判断却先跑 Copilot**。`defaultControl()` 在 runtime=codebuddy 时会把 model 设成 `codebuddy:<默认>`（`src/investigation/control.ts:111-115`），但这个状态不是强制的，配置接口允许 runtime 与 model 分开改。

如果 Copilot 不可用（认证失败、未登录），这是非 quota 错误，`isQuotaError` 为假 → 直接抛出 → 触发 S2 的"拒绝全部工具"。用户看到的是一轮无法推进的调查。

**方向**：辅助调用也传 `runtime: control.agent.runtime`，让"这次 Investigation 用哪个 Runtime"在整条链路上保持一致。

### M2. CodeBuddy 的权限模式形同虚设

`src/agent/codebuddy.ts:293-296` 的 `canUseTool` 对任何非拦截工具都返回 `allow`，没有任何 pending 状态，也没有前端确认桥。相比之下 Copilot 有完整的 `pendingCopilotPermissions` + `respondToCopilotPermission` + 前端 UI（`src/agent/copilot.ts:1099-1204`）。OpenCode 则完全没有权限层。

也就是说，用户在配置里选"需要我逐步确认"（`permissionMode: 'permission'`）时，在 CodeBuddy / OpenCode 上不会收到任何确认请求，工具直接执行。ADR-029 §7 要求失败/交互语义跨 Runtime 一致，这里没有做到。

**方向**：要么在 CodeBuddy 上把 `canUseTool` 接到同一套 `requestAgentUserInput` / permission bridge（CodeBuddy 已经在用 copilot 的用户输入桥，见 `src/agent/codebuddy.ts:24,243`），要么在 UI 上明确告知"该 Runtime 不支持逐步确认"，不要给出一个不生效的选项。

### M3. 结构化输出契约有三套，可靠性不同，调用方无从感知

| Runtime | 结构化输出方式 | 位置 |
|---|---|---|
| Copilot | 原生 `sendAndWait({ responseSchema })` | `src/agent/copilot.ts:1468-1474` |
| CodeBuddy | Schema 作为文本拼进 system prompt，靠解析 | `src/agent/codebuddy.ts:211-216` + `jev-smart-func.ts:332-342` |
| OpenCode | Schema 作为文本拼进 CLI prompt，靠解析 | `src/agent/opencode.ts:555-559` |

同一个 `jevSmartFunc`，在 Copilot 上是"框架保证格式"，在另外两个上是"祈祷模型听话"。而且 OpenCode 里读取 `info.structured_output` 的分支（`src/agent/opencode.ts:504-516`）在现在的 CLI 路径下是死代码——`runOpenCodeCli` 只收集 `text` 类型的 part（`opencode.ts:694-702`），从不产生 `structured_output`。

调用方无法知道当前 runtime 是否具备可靠结构化输出，因此也无法选择"降低概率容差 / 自动重试 / 走非结构化兜底"。这直接放大了 S2。

**方向**：把"是否支持原生结构化输出"作为 runtime capability 暴露出来，让 `jevSmartFunc` 据此调整重试与容差策略。

### M4. 被拒绝后每个工具都重新调用一次 Smart Function

`missionActionReviewed` / `missionActionReviewedExecution` 只在**允许**时置位（`src/agent/codebuddy.ts:290`、`src/agent/copilot.ts:658-660`）。一旦判断为 deny，下一个工具动作会再次触发完整的 `reviewMissionAction` 模型调用。模型如果连续换工具尝试，就会产生一连串额外的 LLM 往返，每个往返在 CodeBuddy/OpenCode 上还是一次完整 Agent query。

**方向**：deny 后在同一阶段内标记"已检查过"，或对同一阶段的 deny 结果做短路，避免模型重试时重复烧模型。

### M5. 每轮隐藏的模型调用数量大，且陪伴提示与主 Agent 并发

一次完整 turn 内，除了主 Agent 的多阶段执行，还会触发：

- 行动闸门：每阶段一次（`ask.ts:532`）
- Unknown 影响判断：每阶段一次（`ask.ts:586`）
- Mission Alignment：有真实状态变化时一次（`ask.ts:614`）
- Mission Completion：**同一轮最多 3 次**——`onStageResult` 里（`ask.ts:657`）、`shouldContinueMission` 里（`ask.ts:790`）、turn 收尾（`ask.ts:925`）
- 人格渲染：一次（`ask.ts:880`）
- 陪伴提示：最多 2 次（`ask.ts:281`），由 `setTimeout(..., 12_000)` 触发（`ask.ts:301-304`）

陪伴提示是**异步并发**发起的，可能在主 Agent 还在跑的时候，同时对同一个 workspace 起第二个 CodeBuddy/OpenCode query。这些调用共享同一个 model/runtime，没有并发预算，也没有配额节流。

**影响**：成本与延迟显著高于"一次提问一次模型调用"的直觉；并发调用在 CodeBuddy/OpenCode 上还可能造成工作区争用。属于设计层面的成本/行为风险，建议做调用预算或合并判断。

### M6. 工作地图 AI 绕过 runtime 选择和 fallback

`generateJourneyFlow` 直接调 `askCopilot`（`src/workflow/journey-ai.ts:179-190`），既不传 model 也不传 runtime，因此永远走 `config.model`（默认 `auto`）→ Copilot 默认路径。它绕过了 `askAgentWithFallback`，所以：

- 不遵循 Investigation 选择的 runtime；
- Copilot quota 用尽时不会 fallback；
- 对 CodeBuddy-only / 无 Copilot 配额的部署直接不可用。

**方向**：与主流程一致，改走 `askAgentWithFallback` 并传 `purpose: 'journey-map'`（该 purpose 已在 runtime 层被识别为隔离用途）。

| # | 问题 | 位置 |

| L1 | 用了 `bypassPermissions` 但未设 `allowDangerouslySkipPermissions`（SDK 注释标注"Require explicit flag"）。即便被降级，`canUseTool` 仍恒 `allow`，所以功能后果相同，但语义上值得核对 CLI 实际行为 | `src/agent/codebuddy.ts:200-202`；SDK `types.d.ts:978` |

## 建议处理顺序

| 序 | 事项 | 理由 |
|---|---|---|
| 1 | S1：给 review/journey-map 用途在 CodeBuddy/OpenCode 上收窄工具面 | 唯一"决策函数能改工作区"的问题，且与设计边界直接冲突 |

| 5 | M2 + M3：权限桥与结构化输出 capability 对齐 | 让三套 runtime 的行为可预期 |
| 6 | M4–M6 | 成本与一致性优化，按实际频率排期 |

## 一句话结论

CodeBuddy、jevSmartFunc 和其它 LLM 执行的问题不在"能不能跑通"，而在**边界不对称**：辅助判断调用借用了完整 Agent 的执行能力（工具、放行、无超时），却没有继承完整 Agent 的约束；同时这些判断的失败被硬耦合进主流程，一次格式偏差就能让整轮调查停摆。这三条严重问题只在 CodeBuddy / OpenCode 上出现，因此在 Copilot 默认路径下不容易被测试和日常使用发现。
