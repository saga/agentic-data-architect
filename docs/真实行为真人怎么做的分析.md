data analyst和data architect，真人的工作流程到底是什么样的，比如现在进入一个项目，对老项目进行改造和重做，希望他们帮忙能理顺当前的data flow和data architecture，他们会怎么做。研究标准模式和业界实际经验。

--------


研究下来，真正做过大型老系统改造的人，工作方式和“先画一张数据架构图，再设计新架构”差别很大。

最接近业界实际的模式是：

> **先建立事实，再建立理解；先还原当前系统，再讨论目标系统。**
>
> Data Analyst 负责把“数据到底发生了什么”查清楚；Data Architect 负责把这些事实组织成架构判断，并决定“应该保留什么、改变什么、怎么迁移”。

而且两个人不是前后串行，通常是**一起推进、反复迭代**。AWS、Google、Microsoft 的 migration/assessment 方法都把 inventory、dependency discovery、stakeholder validation、assessment、migration planning 放在一个连续过程中，而不是先做完整文档再开始技术分析。([AWS Documentation][1])

---

# 一、如果明天真的把一个 Data Analyst + Data Architect 扔进一个老项目

假设背景是：

> 一个老的 Enterprise Operations / Business Operations 平台，要 modernize / replatform。
> 现在没人能完全说清楚：
>
> `Entity Snapshot → Derived Calculation → Analysis → Reporting`
>
> 到底数据从哪里来，经过哪些 ETL，哪个系统才是 source of truth。

他们不会第一天就开始设计 Snowflake 表。

比较真实的工作顺序，大概是下面这样。

---

# 二、阶段 0：先搞清楚“这个项目到底要解决什么”

### Data Architect 主要负责

先确定：

* 改造范围是什么
* 为什么改
* 哪些业务不能受到影响
* 是 rehost、replatform、refactor 还是 replace
* 哪些系统已经决定退役
* 哪些系统暂时必须保留
* 谁是最终决策者
* 哪些 downstream consumer 不能停

### Data Analyst 主要负责

把业务问题具体化：

* 谁现在使用这些数据
* 用户实际看哪些报告
* 哪些数据最关键
* 哪些字段经常出问题
* 哪些手工 Excel / Access / CSV 在实际工作中非常重要
* 哪些“官方文档”实际上没人信

这一步不是形式主义。

CRISP-DM 的 Business Understanding 也是先明确业务目标、成功标准、约束和相关人员，再进入 Data Understanding；公开方法论资料仍然明确把 Business Understanding 和 Data Understanding 分开。

### 第一批产物

不是架构图，而是：

```text
Project Scope
Business Objectives
In-Scope / Out-of-Scope
Stakeholder Map
Critical Business Processes
Critical Data Domains
Constraints / Risks
Key Questions
```

例如投资项目可能先定：

```text
Scope:
- Position
- Reference Data Hub
- Price
- FX
- Derived Value Calculation
- Performance

Consumers:
- Business Operations
- Performance
- Risk
- Client Reporting
- Compliance Reporting

Critical questions:
- Entity state 的 authoritative source 是什么？
- Market Value 到底在哪里计算？
- Price 使用哪个 source？
- Corporate Action 后谁负责调整？
- Historical / as-reported 数据在哪里？
```

---

# 三、阶段 1：先“侦察”，而不是先采访人

这一点非常关键。

真实项目不会完全依靠访谈。

AWS 的详细 assessment 明确建议：**先尽可能利用 programmatic discovery 获取高保真事实，再用访谈补充业务知识和无法自动发现的信息**；AWS 甚至明确指出人工 discovery 在缺乏工具时可能需要数周，而程序化发现可以显著减少工作量。([AWS Documentation][1])

所以实际通常是：

```text
              ┌─ metadata
              ├─ database schema
              ├─ SQL / ETL
              ├─ job scheduler
              ├─ API / file transfer
              ├─ query logs
              ├─ reports / dashboards
              └─ existing documentation
                         ↓
                  Automated Discovery
                         ↓
                 Initial Current State
                         ↓
                  人工访谈进行验证
```

### Data Analyst 会干什么

直接拿 SQL / Python / catalog / scripts 开始查：

```text
有哪些数据库？
有哪些 schema？
有哪些表？
哪些表最大？
哪些表每天更新？
哪些表没人用了？
哪些 SQL 在读它？
哪些 ETL 在写它？
哪些报告用了它？
```

然后找：

```text
Position
Security
Price
Portfolio
Transaction
Performance
Benchmark
FX
```

这些关键对象。

### Data Architect 会看

不是简单看“有多少表”，而是开始建立：

```text
System
  ↓
Application
  ↓
Database
  ↓
Schema
  ↓
Dataset
  ↓
Transformation
  ↓
Consumer
```

以及：

```text
upstream
   ↓
source
   ↓
ingestion
   ↓
transformation
   ↓
curated data
   ↓
analytics
   ↓
report / API / application
```

---

# 四、阶段 2：同时开始访谈，但不是“开会听故事”

这是很多 AI Data Architect 最容易做错的地方。

真人不会只是问：

> “请介绍一下你们的数据架构。”

这种会议通常价值很低。

好的 Data Analyst 会拿着已经发现的事实去问。

比如：

> 我发现 `state_a`、`state_snapshot`、`system_a_state` 三个表都包含 security + quantity。
> 你们认为哪个是 daily business state 的正式来源？

然后继续问：

> 为什么报告 A 用 `state_snapshot`，但是报告 B 用 `system_a_state`？

再问：

> 哪个是 as-of date 的正式值？
> 哪个允许 restatement？
> Corporate Action 之后哪个会变？

这就变成了**证据驱动的访谈**。

AWS 和 Microsoft 的 assessment 指南都强调：自动发现得到 dependency map 后，再由 workload/application owners 进行 structured interviews 来补充工具无法发现的非正式依赖。([Microsoft Learn][3])

---

# 五、阶段 3：不要试图一次还原整个系统，而是追踪几个“关键业务流”

这是整个流程里非常重要的一步。

一个 5000 张表的老系统，不可能一次画清楚。

真人通常会选几个 Critical Business Flow。

比如投资领域：

### Flow 1：Position

```text
Upstream Systems / Operations
        ↓
State Feed
        ↓
System A State
        ↓
Position Snapshot
        ↓
Derived Value Calculation
        ↓
Performance
        ↓
Client Reporting
```

### Flow 2：Price

```text
Bloomberg / Refinitiv
        ↓
Market Data Feed
        ↓
Price Staging
        ↓
Price Normalization
        ↓
Security Price
        ↓
Valuation
```

### Flow 3：Reference Data Hub

```text
Vendor
 ↓
Instrument Feed
 ↓
Security Staging
 ↓
Identifier Mapping
 ↓
Reference Data Hub
 ↓
Position / Price / Research
```

然后对每条 flow 从头到尾追。

# 六、Data Analyst 在这个阶段做的事情，比“写 SQL 查数据”复杂得多

他会真正回答：

### 1. 数据从哪里来？

```text
source system
source table
source file
API
vendor feed
manual spreadsheet
```

### 2. 怎么变化？

```text
filter
join
lookup
dedup
aggregation
calculation
normalization
mapping
```

### 3. 到哪里去？

```text
warehouse
report
application
API
dashboard
downstream feed
```

### 4. 每一步到底做了什么？

比如：

```sql
market_value =
    position_qty
    * close_price
```

但下一步会发现：

```text
close_price
```

又经过：

```text
raw price
→ adjusted price
→ currency conversion
→ valuation price
```

于是原本看起来简单的：

```text
Position × Price
```

实际上变成：

```text
Position
   ↓
Quantity normalization
   ↓
Security mapping
   ↓
Price selection
   ↓
Price adjustment
   ↓
FX conversion
   ↓
Market Value
```

这就是 Data Analyst 真正的价值。

# 七、阶段 4：开始真正“懂数据”，而不是只懂 schema

CRISP-DM 对这一阶段定义得非常接近真实工作：

```text
Collect Initial Data
        ↓
Describe Data
        ↓
Explore Data
        ↓
Verify Data Quality
```

并且强调 Data Understanding 的目标包括理解字段语义、数据分布、质量问题以及形成初始 hypothesis。（公开方法论资料）

所以 Data Analyst 会做：

### Profile

```text
row count
null rate
distinct count
min / max
distribution
duplicate rate
date coverage
update frequency
```

### Explore

例如：

```sql
select security_id, count(*)
from position
group by security_id
order by count(*) desc;
```

再看：

```text
position_qty
price
market_value
currency
as_of_date
```

的分布。

### Reconcile

这是金融项目里极其重要的一步。

例如：

```text
System A State Position
      vs
System B State Position
      vs
Upstream State
      vs
Reporting State
```

发现：

```text
Security A
System A State = 100,000
System B State = 99,500
Custodian = 100,000
```

这个时候 Analyst 不会写一句：

> “System A State is correct.”

而是进一步查：

```text
为什么不同？
trade timing？
settlement？
corporate action？
pricing？
FX？
manual adjustment？
```

当前复杂企业环境公开的岗位职责也非常明确地反映了这一工作方式：一家大型企业的数据岗位 就把 data flow troubleshooting、root-cause analysis、validation、transformation、reconciliation、downstream integration 放在同一职责范围内；另一家大型企业的数据岗位强调 end-to-end data flows、lineage、data ambiguity 和 data-quality impact analysis。（公开企业岗位资料）

# 八、阶段 5：这时候才开始真正建立 Current-State Data Architecture

现在 Architect 才能开始认真画架构。

而且不是一张图。

真正有用的是至少 4 个视图。

## View 1：Business Flow

```text
Business Decision
       ↓
Business Operations
       ↓
Valuation
       ↓
Performance
       ↓
Reporting
```

回答：

> 数据为什么存在？

---

## View 2：System / Data Flow

```text
Market Data
     ↓
Pricing Platform
     ↓
EDW
     ↓
Analytics Platform
     ↓
Reporting
```

回答：

> 数据经过了哪些系统？

---

## View 3：Data Lineage

```text
legacy_state.pos_qty
        ↓
normalized_position.quantity
        ↓
canonical_state.quantity
        ↓
market_value
```

回答：

> 这个字段究竟从哪里来的？

---

## View 4：Logical Data Model

```text
Portfolio
    │
    ├── Position
    │       │
    │       └── Security
    │
    ├── Transaction
    │
    └── Valuation
            │
            ├── Price
            └── FX
```

回答：

> 这些数据概念是什么关系？

# 九、Architect 最关键的工作其实不是“画图”

而是做出几个判断。

例如：

### Source of Truth

```text
Position
  ├── System A State
  ├── System B State
  ├── legacy_state
  └── reporting_state
```

Architect 要回答：

> 哪一个是 authoritative？

但这个答案不是靠架构师“觉得”。

应该形成：

```text
Decision:
System A State is authoritative for intraday investment position

Evidence:
- downstream consumers
- operational process
- reconciliation
- business owner confirmation
- implementation
```

---

### Ownership

比如：

```text
Reference Data Hub
    owner = Business Data
```

还是：

```text
Reference Data Hub
    owner = Operations
```

---

### Business Definition

例如：

```text
Market Value
```

到底是：

```text
Quantity × Price
```

还是：

```text
Quantity × Adjusted Price × FX
```

还是：

```text
official calculation method
```

---

### Temporal semantics

在金融业务里尤其重要：

```text
trade_time
event_time
effective_time
calculation_time
publication_time
knowledge_time
```

Architect 会开始判断：

> 老系统的数据究竟是 current truth、historical truth、as-reported truth，还是 restated truth？

这时候才真正进入 Data Architecture。

---

# 十、阶段 6：把“发现的问题”整理成 Current-State Findings

不是简单写：

> “数据库很复杂。”

而是形成结构化 Finding。

例如：

### Finding 001

```text
Title:
Multiple Position Sources

Evidence:
- system_a_state
- legacy_state
- reporting_state
- 3 downstream reports
- reconciliation result

Impact:
Different consumers may use different position states.

Root Cause:
Historical systems evolved independently.

Risk:
Inconsistent portfolio valuation.

Open Question:
Which source is authoritative for EOD reporting?
```

---

### Finding 002

```text
Identifier Fragmentation

security_id
sec_id
ticker
isin
cusip
internal_security_key
```

然后找到：

```text
AAPL
→ 5 different identifiers
→ 3 mapping tables
→ 2 different reference sources
```

---

### Finding 003

```text
Duplicate Valuation Logic
```

发现：

```text
report_a.sql
    qty * price

report_b.sql
    qty * adjusted_price

derived_value.sql
    qty * price * fx

legacy_report.sql
    pos_qty * px_adj
```

这时候 Architect 才有理由说：

> valuation logic 应该收敛到 domain service / canonical model。

---

# 十一、阶段 7：只有 Current State 基本搞清楚以后，才进入 Target Architecture

TOGAF 的经典模式也是：

```text
Baseline Architecture
        ↓
Target Architecture
        ↓
Gap Analysis
        ↓
Migration Planning
```

其中 Data Architecture 明确要求建立现有 Data Architecture 的 baseline，并根据目标架构做 gap analysis。([AWS Documentation][6])

所以真实项目不是：

```text
Legacy
  ↓
Architect 想一个 Snowflake Architecture
```

而是：

```text
Observed Current State
        ↓
Problems / Constraints
        ↓
Business Requirements
        ↓
Target Principles
        ↓
Alternative Designs
        ↓
Target Architecture
```

---

# 十二、Target Architecture 也不会一步到位

例如最后可能发现：

```text
Legacy
 ├── Position DB
 ├── Security DB
 ├── Price DB
 ├── Reporting DB
 ├── Excel
 └── ETL
```

目标可能是：

```text
External Sources
       ↓
Source Reliability
       ↓
Normalization
       ↓
Canonical Business Data
       ↓
Analytics
       ↓
Semantic Layer
       ↓
Consumers
```

但真正 Architect 要继续回答：

```text
哪些必须保留？
哪些可以 retire？
哪些只能暂时保留？
哪些可以直接 migrate？
哪些必须 redesign？
```

Microsoft 的 migration framework 也明确区分 Retire / Retain / Rehost / Replatform / Refactor / Rearchitect / Rebuild / Replace 等不同处理方式，而不是把所有 workload 当成“迁到新平台”。([Microsoft Learn][7])

---

# 十三、然后才进入 Source-to-Target Mapping

这是 Data Analyst 和 Architect 又一次高度交叉的地方。

例如：

| Source                   | Target                   | Transformation     | Validation                   |
| ------------------------ | ------------------------ | ------------------ | ---------------------------- |
| `legacy_state.sec_id` | `position.security_id`   | security mapping   | mapping coverage             |
| `pos_qty`                | `position.quantity`      | unit normalization | quantity reconciliation      |
| `px_adj`                 | `calculation.price`        | price policy       | price comparison             |
| `ccy`                    | `calculation.currency`     | ISO normalization  | code coverage                |
| `mv_amt`                 | `calculation.derived_value` | recompute          | source/target reconciliation |

注意真正专业的 mapping 不是：

```text
A → A
B → B
```

而是：

```text
source
  ↓
business meaning
  ↓
transformation rule
  ↓
target
  ↓
validation rule
```

Google、AWS、Microsoft 的 migration tooling 都把 mapping / translation / validation 作为独立步骤，而不是单纯复制 schema。([AWS Documentation][8])

---

# 十四、最后才是 Migration / Reconciliation / Cutover

真正的大项目不会：

```text
Design
 ↓
Deploy
```

通常是：

```text
Target Design
    ↓
Pilot
    ↓
Migration Wave 1
    ↓
Reconciliation
    ↓
Fix
    ↓
Wave 2
    ↓
Dual Run
    ↓
Business Sign-off
    ↓
Cutover
    ↓
Rollback window
    ↓
Decommission
```

Microsoft 明确建议按 dependency grouping 做 migration waves，并根据第一批迁移得到的新信息不断调整后续 wave，而不是一开始把所有未来 wave 都锁死。([Microsoft Learn][9])

AWS 对数据迁移同样强调 source/target comparison 和预先定义 validation strategy。([AWS Documentation][10])

# 十五、Data Analyst 和 Data Architect 到底怎么分工

现实中边界没有想象中那么干净，尤其是复杂、强约束的企业环境。

当前大型企业的公开岗位已经出现非常明显的融合趋势。例如 一家大型企业的 Data Strategy 岗位同时要求分析 business datasets/workflows、current-state ecosystem、data quality、lineage，并参与 data architecture、logical models、process flows 和战略规划；其它类似企业岗位也都把 lineage、reconciliation、requirements、testing、data quality 和 data strategy 放在同一工作体系中。（公开企业岗位资料）

但可以用一个非常实用的方式划分：

| 工作                     | Data Analyst  | Data Architect |
| ---------------------- | ------------- | -------------- |
| 业务访谈                   | 主力            | 参与             |
| 数据查询                   | 主力            | 参与             |
| Profiling              | 主力            | 审核             |
| 数据异常调查                 | 主力            | 参与             |
| Reconciliation         | 主力            | 审核规则           |
| Lineage                | 主力发现          | 负责整体视图         |
| Business definition    | 调查            | 确认/治理          |
| Source of truth        | 提供证据          | 做架构判断          |
| Current-state model    | 建数据事实         | 建架构视图          |
| Logical model          | 参与            | 主责             |
| Target architecture    | 输入事实          | 主责             |
| Source-target mapping  | 主力            | 审核             |
| Migration strategy     | 提供数据复杂度       | 主责             |
| Migration waves        | 输入 dependency | 主责             |
| Validation rules       | 主力            | 负责关键标准         |
| Architecture decisions | 输入            | 主责             |

但实际上两者应该形成一个闭环：

```text
                 ┌──────────────┐
                 │ Data Analyst │
                 └──────┬───────┘
                        │ facts
                        ↓
                 ┌──────────────┐
                 │ Data         │
                 │ Architect    │
                 └──────┬───────┘
                        │ hypothesis
                        ↓
                 ┌──────────────┐
                 │ Data Analyst │
                 │ validation   │
                 └──────┬───────┘
                        │ evidence
                        ↓
                 ┌──────────────┐
                 │ Architecture │
                 │ decision     │
                 └──────────────┘
```

这比“Analyst 做完 → Architect 接手”更接近真实项目。

# 十六、整个项目实际上可以压缩成 8 个循环

我认为你这个 `agentic-data-architect` 最应该模拟的其实就是下面这个过程：

```text
1. Scope
   ↓
2. Discover
   ↓
3. Interview / Clarify
   ↓
4. Trace Critical Flows
   ↓
5. Profile / Explore / Reconcile
   ↓
6. Current-State Architecture
   ↓
7. Target Architecture / Mapping
   ↓
8. Migration / Validation
        ↑
        └────── feedback ──────
```

每一轮不是等前一轮 100% 完成，而是不断缩小未知空间。

# 十七、真正的核心不是“生成架构图”，而是消灭 Unknown

一个真人 Data Architect 进老项目，真正会一直在脑子里维护的是：

```text
我们已经知道什么？
我们以为知道什么？
哪里是证据？
哪里只是某个人说的？
哪里互相矛盾？
哪些东西还不知道？
哪些 Unknown 会影响架构决策？
```

所以一个很真实的工作状态可能是：

```text
Position source
    ✅ technically observed: System A State

Authoritative?
    ⚠️ business confirmation pending

EOD definition
    ⚠️ conflicting documentation

Corporate action adjustment
    ❓ undocumented

Legacy reporting position
    ✅ observed

Relationship to System A State
    ❓ unknown

Market value calculation
    ✅ SQL found

Price precedence
    ⚠️ 3 competing implementations
```

这种状态其实比“一张很漂亮的架构图”有价值很多。

# 十八、这对 `agentic-data-architect` 的意义非常直接

按照这次研究，我会把你项目的定位稍微改一下：

不是：

> **AI Data Architect 可以帮你设计数据架构**

而是：

> **AI Data Architect 模拟一个 Data Analyst + Data Architect 团队，对既有数据系统进行 Brownfield Discovery、Current-State Reconstruction、Architecture Analysis 和 Modernization Design。**

因此产品真正的主线应该是：

```text
Investigation
     ↓
Scope
     ↓
Evidence Discovery
     ↓
Data / System Inventory
     ↓
Critical Flow Analysis
     ↓
Lineage + Profiling
     ↓
Business / SME Validation
     ↓
Current-State Reconstruction
     ↓
Findings / Conflicts / Unknowns
     ↓
Source-of-Truth Decisions
     ↓
Target Architecture
     ↓
Source-to-Target Mapping
     ↓
Migration & Validation Plan
```

而不是：

```text
Upload SQL
   ↓
LLM
   ↓
Architecture Document
```

这个差别非常大。

你现在项目里的 **Evidence、Estate Graph、Inventory、Lineage、Profiling、Finding、Unknown、Investigation** 其实方向是对的，但按照真人工作流程，还缺一个很重要的概念：

> **Critical Business Flow / Investigation Thread**

因为真人不是对整个 estate 平均分析，而是：

```text
先选一个业务问题
→ 从消费者一路向上追
→ 找数据来源
→ 找 transformations
→ profile
→ reconcile
→ 找 owner
→ 找 definition
→ 发现冲突
→ 再扩展 investigation scope
```

这很可能应该成为你 `agentic-data-architect` 的核心交互单位。

另外一个很明显的结论是：**Data Analyst 的工作不能只设计成 `ask(question)`。** 真人 Analyst 实际上大量时间是在做：

```text
trace()
profile()
compare()
reconcile()
inspect()
find_dependency()
find_definition()
find_conflict()
validate_hypothesis()
```

然后才是：

```text
ask()
```

所以从业界实际工作流程反推，你这个项目下一步最值得补的，很可能不是再增加一个 Agent，而是把 **Investigation / Critical Flow / Hypothesis / Evidence / Validation** 这一套工作循环真正做出来。
