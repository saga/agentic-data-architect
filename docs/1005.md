这个问题我认为是当前 Agent“跑偏”的一个核心原因，而且不能只靠多写几句 Prompt 解决。应该把“任务目的”和“期望结果”提升成整个 Investigation 的 **Mission Contract（任务契约）**，从输入、Prompt、Workflow、阶段推进到最终结果都围绕它。

## 一、先定一个核心原则

以后整个 Investigation 只认一个东西：

> **这次为什么做？最终要交付什么？**

Workflow、Skill、unknown、route、Agent 自己想到的问题，都只能服务于它们，不能反过来定义任务。

例如用户：

> 分析 某大型企业 的老系统，给出 replatform 方案。

系统应该固定形成：

```text
任务目的
理解 某大型企业 老系统当前的数据架构，为 replatform 决策提供依据。

期望结果
1. 当前 Data Source
2. 当前 Data Flow
3. 当前 Data Model
4. 关键业务/数据转换
5. replatform 目标方案
6. 新旧系统对应关系
7. 验证思路
```

然后整个 Agent 执行过程中反复拿这两项作为“尺子”。

# 二、不要只把它放在 Prompt，而要成为持久化状态

现在 `context.json` 有：

```text
goal
scope
systems
questions
unknowns
...
```

但没有一个真正的 **任务契约**。

建议新增：

```ts
mission: {
  purpose: string;
  expectedResult: string;
  deliverables: Array<{
    id: string;
    title: string;
    description: string;
    required: boolean;
  }>;
  confirmedAt: string;
  confirmedBy: 'user';
}
```

这里最关键的是：

### `purpose`

回答：

> 为什么做这件事？

### `expectedResult`

回答：

> 最后你到底希望拿到什么？

### `deliverables`

把 expectedResult 拆成几个可以检查的交付物。

例如：

```text
purpose:
理解 某大型企业 老系统，为 replatform 提供依据

expectedResult:
获得当前数据架构并形成 replatform 方案

deliverables:
- data-source
- data-flow
- data-model
- transformation
- target-architecture
- migration-mapping
- validation
```

这样以后系统才有可能真正判断：

> “我现在查这个东西，到底是在帮助完成哪一个结果？”

# 三、任务启动必须增加一个真正的 Mission Gate

这是最重要的一层。

现在已有 `Scope Gate`：

```text
Goal / Scope / Systems
```

但我建议新增：

```text
Mission Gate
```

顺序应该是：

```text
新建 Investigation
       ↓
Mission Gate
       ↓
任务目的明确？
期望结果明确？
       ↓
否
 ↓
ask_user
       ↓
确认后保存 Mission
       ↓
Scope Gate
       ↓
Discovery / Agent
```

### 规则非常简单

如果：

```text
purpose 缺失
OR
expectedResult 缺失
OR
内容太模糊
```

**禁止开始调查。**

不能：

```text
“先帮用户搜搜看”
“先跑 discover”
“先看看代码”
```

因为这正是你现在遇到的问题来源之一。

# 四、但不能简单靠字符串非空判断“清晰”

这里我建议刚刚做好的 `jevSmartFunc` 正好派上用场。

分两层：

### Script Gate

确定：

```text
有没有 purpose
有没有 expectedResult
是否已经用户确认
```

### Smart Function

判断：

```text
这个 purpose 是否足够清晰？
这个 expectedResult 是否足够明确？
两者是否一致？
```

例如：

```text
purpose:
看看这个系统

expectedResult:
给我一些分析
```

Script 看起来都有值，但明显没有用。

可以：

```text
jevSmartFunc({
  prompt: "判断任务目的和期望结果是否足够明确，可以开始执行调查",
  context: {
    purpose,
    expectedResult
  },
  questions: {
    clear: {
      type: "noul",
      ...
    },
    quality: {
      type: "score",
      ...
    }
  }
})
```

如果不清楚：

> 先问用户。

而不是让 Agent 自己猜。

# 五、Prompt 要重新设计：Mission 放到最高位置

这是你现在最应该改的地方。

现在 `LEAD_SYSTEM_PROMPT` 里面虽然已经有目标、scope 等信息，但比较散。

应该建立统一函数：

```ts
buildMissionContractPrompt(mission)
```

然后每一轮都放在 **system prompt 的第一块**：

```text
## Mission Contract

这是本次 Investigation 必须完成的任务。

### 任务目的
理解 某大型企业 老系统，为 replatform 提供决策依据。

### 期望结果
获得当前 Data Source、Data Flow、Data Model，
并形成可落地的 replatform 方案。

### 必须交付
- Data Source
- Data Flow
- Data Model
- Transformation
- Target Architecture
- Migration Mapping
- Validation

### 执行原则
1. 所有调查动作必须直接服务于上述目标。
2. unknown 只是未知，不是待办清单。
3. 不要因为发现了一个有趣问题就改变调查方向。
4. 如果已经足够支持期望结果，就停止继续深挖。
5. Workflow 只是执行路线，不能改变 Mission。
6. 如果发现 Mission 本身存在歧义，先问用户。
```

然后才是：

```text
## Active Workflow
## Skills
## Research Configuration
## Current Evidence
## Conversation
```

也就是说：

```text
Mission
  ↓
Workflow
  ↓
Skill
  ↓
Evidence
  ↓
当前具体问题
```

而不是现在比较容易变成：

```text
当前 Workflow
  ↓
发现一个问题
  ↓
Agent 自己继续
```

# 六、每一轮都必须重新强调 Mission，但不要人工复制几十遍

不是每个地方手写一遍。

应该做成一个统一模块：

```ts
buildMissionContractPrompt(mission)
```

然后所有重要 Prompt 都调用：

```text
askCopilot()
  ├─ Mission Contract
  ├─ Lead System Prompt
  ├─ Workflow
  ├─ Knowledge
  ├─ Context
  └─ Current Question
```

需要保证至少进入：

### 1. Lead Agent

最重要。

### 2. Workflow instruction

明确：

> Workflow 不得改变 Mission。

### 3. 自动续跑阶段

每次 continuation 都重新注入 Mission，而不是只依赖 Copilot Session 里的旧上下文。

这是非常重要的。

因为现在你用了 persistent Copilot Session，多轮之后模型上下文里会出现很多东西：

```text
用户原始目标
→ 第一轮问题
→ route
→ unknown
→ 第二轮问题
→ tool result
→ 某个局部细节
...
```

越到后面，原始目标越容易被淹没。

所以：

> **Mission 必须每轮重新放到 system prompt 第一位置。**

# 七、selectedRoute 不能覆盖原任务

这里当前代码其实有一个比较明显的风险：

```ts
const effectiveQuestion = selectedRoute
  ? '选择下一步：' + selectedRoute.title
  : question;
```

这会让当前这一轮的“问题”变成：

> 选择下一步：查 XXX

但真正的用户任务是：

> 分析 某大型企业 老系统并给出 replatform 方案。

建议以后变成：

```text
Mission
↓
User Request
↓
Selected Route / Current Subtask
```

也就是说 route 只是：

> 当前为了 Mission 而执行的一个动作。

而不是把 Mission 替换成 route。

这是我认为必须改的一个地方。

# 八、unknowns 要重新定义

现在已经有：

> unknowns 不是任务队列

但还不够。

应该明确成：

```text
unknown
   ↓
是否影响 expectedResult？
   ↓
否 → 保留记录，不继续查
是
   ↓
能否自己解决？
   ↓
是 → 自己查
否 → 问用户
```

所以 Agent 不能因为：

```text
“这个业务定义我还不知道”
```

就自动进入另一个分支。

必须先问：

> 这个未知是否阻碍当前期望结果？

这会直接解决你截图里“查关键问题”的问题。

# 九、阶段推进也应该围绕 Mission，而不是围绕 Workflow

未来阶段完成应该是：

```text
Mission
 ↓
当前阶段应该贡献哪个结果？
 ↓
实际产生了什么成果？
 ↓
Stage Gate
 ↓
继续 / 停止 / 进入下一阶段
```

而不是：

```text
Workflow node
 ↓
Agent 觉得差不多
 ↓
success
```

这里我们刚刚做的 Stage Script Gate 可以继续用。

但我建议下一步再增强它：

```text
Stage Gate

1. 有没有真实调查成果？         Script
2. Evidence 是否有效？           Script
3. 是否属于当前 Mission 目标？   Smart Function
4. 是否值得继续？                Smart Function
5. 是否允许推进 Workflow？       Script
```

这样三者分工非常清晰：

```text
Agent
做调查

jevSmartFunc
做“这个东西对任务有没有用”这种判断

Script Gate
做最终确定性裁决
```

# 十、最好把 Mission 的“交付物”也纳入阶段成果

这是这个方案里我最推荐加的一点。

例如：

```text
Mission Deliverables

[✓] Data Source
[✓] Data Flow
[ ] Data Model
[ ] Transformation
[ ] Target Architecture
[ ] Mapping
[ ] Validation
```

这样 Agent 每一轮不是想着：

> “还有什么问题可以查？”

而是：

> “用户要的东西，我还缺什么？”

这两个思维方式完全不同。

你的截图里现在最明显的问题就是：

```text
已经知道很多东西
        ↓
但是 Agent 还在寻找“问题”
```

应该变成：

```text
Data Source    ✓
Data Flow      ✓
Data Model     ✓
Transformation △
Target         ×
Mapping        ×
Validation     ×
```

然后自然知道下一步应该干什么。

# 十一、对这个产品，最终推荐的整体结构

Mission 现在不只是 Prompt 里的几句话，而是 Investigation 的最高优先级约束：

```text
                         Mission
                  ┌──────────────────┐
                  │ 为什么做          │
                  │ 最终要什么        │
                  │ 必须交付什么      │
                  └────────┬─────────┘
                           ↓
                     Mission Gate
                           ↓
                    Scope / Discovery
                           ↓
                 行动前 Mission Check
                 “这个动作该不该现在做？”
                           ↓
                    Workflow / Skill
                           ↓
                 Evidence / Findings
                           ↓
                    Stage Gate
             “本阶段是否真的产生了结果？”
                           ↓
                 Deliverable Coverage
                           ↓
              Unknown Impact Review
      ignore / Agent 自查 / ask_user
                           ↓
                Mission Completion
        “用户最终要的结果是否已经足够？”
                           ↓
                       停止 / 继续
```

这里有三个需要特别区分的层次：

1. **Action Gate**：防止 Agent 还没有明确服务对象就开始查。每个自动续跑阶段只检查第一个实质调查动作，识别它服务哪个 deliverable、现在是否真的必要；之后靠 Stage Gate 检查实际结果，避免每个 grep / view / bash 都额外调用一次模型。
2. **Unknown Review**：unknown 只是状态。系统会判断它是否影响 Mission、现在是否值得查、Agent 能不能自己解决，然后确定性分流为 `ignore`、`investigate` 或 `ask_user`。因此“有 unknown”本身不再意味着“继续找问题”。
3. **Mission Completion**：Workflow 的 `completed` 只表示路线节点完成，不等于用户目标完成。只有必需交付物没有明确缺口，并且 Smart Function 判断现有结果足够支撑 expectedResult，Mission 才真正结束。

# 十二、实际代码边界

这套机制继续保持“小而明确”，不增加 `MissionWorkflowEngine`、`GoalPlanner`、`TaskPlanner` 这类大框架。

| 文件 | 职责 |
| --- | --- |
| `src/investigation/schemas.ts` | 持久化 Mission Contract |
| `src/workflow/mission-gate.ts` | Mission 启动 / 边界检查 |
| `src/agent/prompts.ts` | 每轮最高优先级 Mission Prompt |
| `src/agent/jev-smart-func.ts` | Action / Alignment / Unknown 三类语义判断 |
| `src/workflow/mission-progress.ts` | deliverable 覆盖计算 |

| `skills/legacy-modernization/SKILL.md` | 在既有 Workflow 下围绕 Mission deliverables 工作 |

# 十三、最关键的一句话

以后 Agent 每一轮实际执行的是：

```text
我为什么在做这件事？
        ↓
用户最终要什么？
        ↓
当前已有结果覆盖了什么？
        ↓
现在做什么最能帮助完成剩余结果？
        ↓
这个动作有没有必要？
        ↓
做完以后检查真实结果
        ↓
Unknown 是否真的影响 Mission？
        ↓
最终结果够不够？
        ↓
继续 / 问用户 / 停止
```

而不是：

```text
我现在发现了什么？
→ 这个东西还有什么未知？
→ 再查这个未知
→ 又发现一个问题
→ 再查问题
```

后者才是“问题驱动跑偏”。

当前实现已经把前面的 Mission 驱动闭环落到代码：**Mission 先于 Workflow，行动前先校准，unknown 不再自动变任务，Workflow 完成不等于 Mission 完成。**
