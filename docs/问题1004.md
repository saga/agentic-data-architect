我仔细把当前 `main` 的 **Workflow、Journey、Investigation、Discovery、Evidence、Agent Runtime、GitHub Skill、工作产物和 UI** 串起来看了一遍。

结论很明确：

> **现在真正的问题不是“Agent 不够自主”，也不是“自动续跑次数太少”。**
>
> **而是产品想做的是“围绕一个架构任务持续完成研究”，代码实际上实现的是“围绕一次用户问题做 Evidence-first 问答，再用 Workflow 做阶段导航”。**
>
> 两者不是一回事。

这也是为什么你现在会感觉它：

> “我明明给了一个完整架构任务，AI 却天天问我一些很小的问题。”

# 一、第一根本问题：你给的是“任务”，系统把它当成了“问题”

这是当前最核心的问题。

你真正的输入是：

```text
给我一个 GitHub repo
↓
研究当前系统
↓
搞清 data flow
↓
找到数据模型
↓
找到数据源
↓
理解关键架构
↓
找出问题
↓
设计新的 target architecture
```

这实际上是一个：

```text
Architecture Investigation / Design Task
```

但当前主入口 `answerQuestion()` 的抽象还是：

```text
用户问题
    ↓
buildQuestionPrompt()
    ↓
Copilot
    ↓
answer
    ↓
claims
    ↓
unknowns
    ↓
followUpQuestions
```

也就是说，整个 Agent runtime 的第一公民仍然是：

> **Question / Answer**

而不是：

> **Task / Investigation / Deliverable**

这就决定了它天然容易出现：

```text
“这个问题是什么？”
“这个证据还缺什么？”
“下一步可以查 X”
“你要不要继续？”
```

而不是：

```text
“我要完成这个架构任务。”
“当前要完成的主要工作有 6 件。”
“现在已经完成 2 件。”
“第 3 件受阻，我先做第 4 件。”
“现状已经足够清楚，现在开始设计 Target Architecture。”
```

# 二、第二根本问题：`goal` 甚至没有正确进入 Investigation

这个是代码层面的硬伤，而且和你看到的：

> **“这次分析最终要回答什么具体问题？”**

直接对应。

新建调查 UI 里其实有：

```text
newSessionGoal
```

但是创建 Session 时：

```text
userPrompt: newSessionGoal
```

然后：

```ts
newInvestigation(...)
```

里面实际上是：

```ts
goal: '',
userPrompt,
```

也就是说：

```text
用户填写“目标”
       ↓
userPrompt
       ↓
没有进入 goal
```

而 `answerQuestion()` 构造 Agent Prompt 时：

```text
goal: inv.goal
```

所以 Agent 收到的是：

```text
目标：（未设置）
```

但它明明能看到：

```text
userPrompt = “……”
```

这就是一个非常严重的状态定义错误：

```text
userPrompt
    ≠
goal
```

而你产品实际上又把两者当成了不同东西。

# 三、更加糟糕：Journey 和 Agent 对“目标”的理解还不一致

这就是为什么当前系统会出现非常诡异的状态。

`buildJourneyFacts()` 用的是：

```text
context.goal || context.userPrompt
```

所以 Journey 说：

> 我有目标，可以继续。

但 `answerQuestion()` 用的是：

```text
inv.goal
```

所以 Agent 说：

> 目标还不知道。

于是就可能发生：

```text
工作地图：
✓ 接到任务
→ 看清旧系统

Agent：
“这次分析最终要回答什么具体问题？”
```

这是典型的：

> **同一个领域概念存在两个事实来源。**

而且两个来源的优先级还不同。

这比单纯 Prompt 写得不好严重得多。

# 四、第三根本问题：你最需要的“GitHub → 当前系统事实”这条链根本没有打通

这是我认为整个项目现在最大的架构缺口。

你现在的输入经常是：



支持的是：


也就是：

```text

```

而不是：


这条链完全围绕：

设计。

中间出现了一个大断层：

这就是为什么你之前的 Agent 会说：

> “源码检查显示……”

然后马上又说：

> “当前允许引用的 Evidence 只有三份 REST 文件记录，不能用它们支持服务到数据库表的映射结论。”

**这个矛盾不是 Agent 傻。**

它是在遵守你自己设计的 Evidence 规则。

# 七、第五根本问题：Work Map 实际上不是“任务地图”，只是“Workflow 状态机”

这点非常关键。

```text

 ↓
```

而不是：

# 十五、你现在真正需要的“工作地图”其实不是 Workflow Map

这是我重新审核后最重要的判断。

你现在的：

> Journey Map

是：

> **Workflow Map**

它解决的是：

> Data Architect 一般先做什么，再做什么。

但你现在真正需要的是：

> **Investigation Map**

它解决的是：

> **这一次具体的架构任务，现在要完成哪些事情。**

举你的例子：

```text
Open Liberty Modernization
────────────────────────────────

① 了解系统
   ✓ REST endpoints
   ✓ Open Liberty / EJB
   → 主要模块

② 搞清数据模型
   ✓ Customer
   → Product
   → Category

③ 搞清数据来源
   → DB2
   → DDL
   → application config

④ 搞清数据流
   → REST → Service
   → Service → Entity
   → Entity → Table

⑤ 找关键业务逻辑
   → Order
   → Customer
   → Product

⑥ 设计 Target Architecture
   ○ Data model
   ○ Data sources
   ○ ingestion
   ○ semantic layer
   ○ serving

⑦ 形成迁移方案
   ○ mapping
   ○ validation
```

这张东西才真正像你要的：

> **Data Architect 工作地图。**

而且它完全不需要成为一个复杂的新引擎。

# 十六、因此我现在给当前架构下一个结论

# 最后，用一句话解释你现在看到的所有怪现象

你现在真正想要的是：

```text
“帮我完成一个架构任务。”
```

但系统实际问 Agent 的问题是：

```text
“回答我这一轮问题，并给我几个下一步按钮。”
```

再加上：

```text
用户给 GitHub
    ↓
GitHub 研究结果没有天然进入 Evidence
    ↓
Current State 不完整
    ↓
Workflow 无法获得真实进展
    ↓
Agent 又没有真正的 Work Product 目标
    ↓
于是退化成最安全的行为：
找一个很小的问题
→ 查一点
→ 生成 unknown
→ 推荐一个很小的下一步
→ 停
```

所以你现在看到的“若智感”其实是**系统架构把 Agent 逼成这样的**，不是简单把 Prompt 再写猛一点就能解决。

**我现在不会改代码。下一步真正应该做的是先把这个架构重新收敛成一个非常简单的模型：`Investigation Goal → 当前工作阶段 → Evidence/State → Work Product → Agent 持续推进`，然后再决定现有 Workflow/Journey 哪些保留、哪些降级、哪些删除。**
