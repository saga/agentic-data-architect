# ADR-035：多语言结构分析采用 Provider + Artifact Extractor，而不是统一 Tree-sitter 化\n\n- Status: Accepted\n- Date: 2026-10-08\n- Supersedes: None\n\n## Context\n\n移除 Graphify 后，Code Structure Index 成为唯一结构分析能力。当前实现使用 TypeScript compiler API，能够较好地分析 TS/JS 的声明、模块解析和调用关系。\n\n实际 Investigation 的代码库可能同时包含 Java、Python、C#、SQL，以及 Control-M、SnapLogic、Snowflake 等数据工程/集成工件。不能因为需要跨语言，就把所有内容强行塞进一个 Tree-sitter parser。\n\nGraphify 的值得借鉴之处主要是“确定性解析 → 持久化结构索引 → 有界查询”、EXTRACTED/INFERRED/AMBIGUOUS 的证据区分、按语言独立 extractor、内容 hash 缓存和 fixture-based tests，而不是其完整 graph/database/runtime 产品面。Graphify v8 也对 SQL 做了专门的表、视图、外键和 JOIN 提取，而不是把 SQL 当普通函数调用图处理。\n\n## Decision\n\n### 1. Provider 分层\n\nCode Structure Index 保持统一 provider 边界：\n\n- TypeScript/JavaScript：继续使用 TypeScript compiler API。\n- Java/Python/C#：优先增加 Tree-sitter provider/extractors。\n- SQL：增加专用 SQL extractor；Tree-sitter 可以作为 CST/语法基础，但 lineage、table、view、JOIN 等必须由 SQL-specific extraction 规则产生。\n- 其他语言按真实 Investigation 需求增量增加，不预先实现“大而全”的语言平台。\n\nTree-sitter 是解析基础设施，不是 Code Structure Index 的公共数据模型。\n\n### 2. 当前实现状态

已经实现：TS/JS compiler provider、Java/Python/C# Tree-sitter provider、SQL provider，以及统一的 canonical composite provider。Java/Python/C# 的 Tree-sitter runtime 使用 Microsoft 的 `@vscode/tree-sitter-wasm` 预构建包（当前锁定 0.3.x），grammar 以独立 WASM 文件加载；不再依赖各语言的 native `tree-sitter-*` Node binding。SQL 当前以 `node-sql-parser` 为基础并保留 dialect 参数边界；Snowflake-specific SQL 语法仍由后续 dialect extractor 处理，不伪装成 MySQL 解析结果。

选择 WASM 的原因是这里更关注本机工作台的可移植性和稳定安装：同一套 grammar 不依赖平台 native addon 编译，同时保留 Tree-sitter 的确定性 AST 能力。代价是 WASM 解析通常比 native binding 更慢，因此只用于当前 Java/Python/C# 的结构索引，不扩大到所有代码与 SQL 处理。

### 3. 代码语言优先级\n\n第一优先级：\n\n1. Java\n2. Python\n3. C#\n4. SQL\n\n第二优先级，出现真实项目需求再增加：\n\n- C/C++\n- Go\n- Kotlin\n- Scala\n- COBOL\n- PL/SQL / Oracle SQL dialect\n- DB2 SQL dialect\n- Terraform/HCL\n\n### 4. 非代码工件不强行使用 Tree-sitter\n\n以下对象不是“语言 parser”问题，应使用 artifact-specific extractor：\n\n- Control-M：解析其 job / folder / dependency 定义（通常 XML/JSON/导出文本），建立 job、folder、schedule、dependency 等节点。\n- SnapLogic：解析 pipeline/export JSON，建立 pipeline、task、account/reference、document flow 等节点。\n- Snowflake：SQL 使用 SQL extractor；数据库真实对象、依赖、ownership、DDL 等优先来自 Snowflake metadata，而不是静态 parser。\n- YAML/JSON/XML：只在它们承载架构有意义的配置时增加轻量 artifact extractor，不把每个配置键都变成图节点。\n\n### 5. 公共模型\n\n不同 parser 最终统一到 Code Structure Index 的最小模型。第一阶段保留：\n\n- file\n- class\n- function\n- interface\n- type\n\n后续只有当真实 Investigation 需要时再增加：\n\n- method\n- table\n- view\n- job\n- pipeline\n- module/package\n\n每条关系必须标记：\n\n- exact：源文件中直接可确认\n- inferred：通过静态解析/解析规则推导\n- 不确定关系不进入 exact 关系；必要时单独标记 ambiguous/candidate，而不是伪装成确定关系。\n\n### 6. Stable ID\n\n节点 ID 使用：\n\nfile + kind + name + same-name ordinal\n\n不得使用行号、字符 offset 或 hash 作为节点身份。源码前面插入空行、注释或其他不影响实体身份的文本后，原实体 ID 必须保持稳定。\n\n### 7. 不建设统一 Graph Database\n\nJSON snapshot 继续作为 canonical structural fact boundary。DuckDB 可以作为该 snapshot 的可重建 analytical projection 和查询实现，但不拥有独立事实源。Tree-sitter、SQL parser、artifact extractor 都只负责产生结构事实；find / callers / callees / trace 继续作为最小查询接口。详见 ADR-036。\n\n如果未来确实需要社区发现、中心性、复杂子图查询，再单独形成 ADR；当前不为了跨语言而引入 NetworkX/Neo4j/图数据库。\n\n## Consequences\n\n- TS/JS 保留 compiler API 的类型和模块解析优势。\n- Java/Python/C# 可以以较低成本进入统一结构模型。\n- SQL 能真正服务 Data Architecture Investigation，而不是只得到“SQL 里有函数调用”的错误抽象。\n- Control-M、SnapLogic、Snowflake 能表达业务架构中的真实对象，而不会被错误建模成普通源代码。\n- parser 增加仍然是可控的；每个语言/工件都有独立 extractor 和 fixture tests。\n\n## Rejected alternatives\n\n### A. 全部改成 Tree-sitter\n\n拒绝。TS/JS 当前 compiler API 已经可用，强行迁移会丢失现有模块解析优势，而且不能解决 SQL / Control-M / SnapLogic / Snowflake 的领域语义问题。\n\n### B. 直接复刻 Graphify 的 30+ 语言\n\n拒绝。当前 Investigation 需要的是有价值的结构导航，不是通用代码知识图谱产品。语言覆盖应由真实仓库类型驱动。\n\n### C. 把 Control-M / SnapLogic / Snowflake 都当作 Tree-sitter language\n\n拒绝。这些首先是调度、集成 pipeline 和数据库平台工件，应采用领域 extractor + live metadata，而不是伪造语言 grammar。\n
